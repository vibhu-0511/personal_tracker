# ADR-0003: Sync v2 design decisions

- Status: Accepted (design). Running the SQL on the live Supabase project still needs the user's approval (open decision D16, default assumed: approval at the time, backup first, per-key flags and rollback).
- Task: B1-04. Depends on B1-01 (docs/plan/blueprint-errata.md, items E-10 to E-13).
- Records the outcome of R6's schema proposal (docs/plan/research/R6-report.md and R6-sync-v2.sql). Where this ADR and the blueprint (docs/plan/blueprint.txt, section 2.4) differ, this ADR wins for sync v2.
- Not verified here: real Supabase behaviour (Realtime delivery, pg_cron, the real `auth.uid()`). R6 validated the SQL only on a throwaway PostgreSQL 16 with a stubbed auth schema.

## Context

Sync v1 stores each of the 17 keys in `SYNCED_KEYS` (src/store.js) as one JSON blob per key in `kv_store`. The client wraps a value as `{data, updatedAt}` (src/sync/logic.js) and `decideSync` compares whole-key timestamps. The timestamp is the client's `Date.now()`, and the cloud `updated_at` is also written from the client clock.

This is correct for one writer per key at a time. It loses data in three ways, which are the reasons for v2:

1. Granularity. A debounced edit (700 ms, src/sync/engine.js) re-uploads the whole key. Two devices that edit different records of one list while offline both take the "newer wins" branch, and one edit disappears. (Errata E-13: the problem is the debounced edit, not each keystroke, but the conclusion is unchanged.)
2. Clock trust. A device with a wrong clock wins until the others write later than it.
3. Deletes. A delete is just a shorter list, so a stale device can bring a deleted record back, and nothing records that a delete happened.

The blueprint's v2 sketch (one table per entity, `rev bigint generated always as identity`, "server clock wins ties") has three defects, recorded in errata E-10, E-11 and E-12:

- An identity column is assigned on INSERT only, so `where rev > last_seen_rev` never sees an update or a tombstone.
- There is no HLC column, and "server clock wins ties" is a different rule from HLC ordering.
- `id uuid primary key` per entity fits only the 10 id-list keys. The other 7 keys are maps, a by-date list and objects.

## Decision summary

| Topic | Decision |
|---|---|
| Table layout | One generic table `public.records`, primary key `(user_id, collection, id)`, `id` is text. Not one table per entity. |
| `rev` | Drawn from a sequence by a `BEFORE INSERT OR UPDATE` trigger on every write. Never `generated always as identity`. |
| Cursor | One cursor per table: `rev > cursor - 50` with a 50-row overlap, de-duplicated by `hlc`. |
| Clock | `hlc text collate "C"` column. Winner is decided by HLC comparison only. No "server clock wins ties". |
| Deletes | Tombstone rows (`deleted_at`, `body` null). Clients cannot physically delete. |
| Tombstone GC | Server-side, 90 days. A device offline for more than 60 days does a full resync. |
| Key coverage | All 17 `SYNCED_KEYS`, in families, with `habits.checkins` split out into its own collection. |
| Migration | Per-key flag, SQL backfill, dual-write of the v1 blob for 14 days, verify before cutover, rollback per key. |
| `kv_store` | Never dropped or renamed (public/dsa/mastery-map.html writes it directly under the key `dsa_mastery_v1`). |

## 1. One generic `records` table

Shape (R6-sync-v2.sql section 1 is the exact DDL):

| Column | Type | Rule |
|---|---|---|
| `user_id` | uuid | default `auth.uid()`, references `auth.users` on delete cascade |
| `collection` | text | the synced key name, for example `tasks`; check `^[A-Za-z][A-Za-z0-9_]{0,39}$` |
| `id` | text | `String(item.id)`, the map key, or a date; 1 to 200 characters |
| `body` | jsonb | null only on a tombstone; under 256 KiB |
| `pos` | double precision | fractional order index for ordered lists |
| `hlc` | text collate "C" | see section 3 |
| `device_id` | text | writer, for audit and for the v1 retirement check |
| `deleted_at` | timestamptz | tombstone marker; check `(deleted_at is null) = (body is not null)` |
| `rev` | bigint | see section 2 |
| `server_at` | timestamptz | set by the trigger on every write |

Why one table: 17 keys but 4 shapes, the field sets have changed several times since August, no server-side querying of record fields is needed, and one table means one set of RLS policies, one Realtime channel and one cursor. This deliberately departs from the blueprint's "same shape for habits, expenses, loans..." sketch.

RLS is owner-only: select, insert and update policies on `(select auth.uid()) = user_id`. There is no DELETE policy and no DELETE grant, so a client cannot physically delete a row.

Writes go through the batched, idempotent RPC `forge_push(rows jsonb)` (security invoker, so RLS applies). It upserts with `where t.hlc < excluded.hlc`, so a replayed or reordered op changes nothing, and it drops a row whose HLC wall time is more than 24 hours ahead of the server clock.

## 2. Decision: `rev` bumps on every write (trigger)

- `rev` is assigned from the sequence `public.records_rev_seq` in a `BEFORE INSERT OR UPDATE` trigger (`records_stamp`), together with `server_at := now()`. R6 observed the value increase on update in its throwaway PostgreSQL 16 run.
- A tombstone is an UPDATE of a row, so it also gets a new `rev` and reaches every device's delta pull. Deletes are therefore Realtime UPDATE events, and default replica identity is enough.
- `rev` is a transport cursor only. It never decides which edit wins.
- Index `(user_id, rev)` serves the delta pull.

## 3. Decision: HLC column and ordering

- Column `hlc text collate "C" not null`, format `<15-digit ms>-<4 hex counter>-<device node>`. A CHECK pins the first two parts. The `collate "C"` makes string order equal causal order in both JavaScript and SQL, and SQL `substr(hlc, 1, 15)` reads the wall part.
- The same string format is the contract for the client clock (X1-16 `hlc.js`, format pinned by R6-02).
- Client clock: `send()` is `max(wall, last)` plus counter. `receive(remote)` is `max(wall, last, remote)` plus counter. A remote HLC more than 24 hours ahead is rejected, so one wrong-clock device cannot poison the others. The same guard exists inside `forge_push`.
- Winner: the larger HLC string wins. The device node is part of the string, so ties are broken by node id and the order is total. Equal HLC is a no-op, which makes a device's own Realtime echo free. Blueprint Lab 1's rule that the phone wins ties is replaced by this.
- Exception, moodLog only: a record with `source: 'logged'` beats `source: 'derived'` regardless of HLC, because two devices can derive the same date and must not overwrite a manual entry.

## 4. Decision: one cursor per table

- Each table has its own sequence, so a cursor is per table. Today there is one table, `records`, so there is one cursor, kept locally as `r2:meta.cursor` together with the user id and device id.
- Pull: `where user_id = auth.uid() and rev > cursor - 50`, then merge each row only if `incoming.hlc > local.hlc`. The overlap exists because sequence values can become visible out of order when transactions commit out of order. De-duplication by HLC makes re-reading rows harmless.
- If a later phase adds another table (for example a separate collection for Pencil drawings, open decision D17, which is a new `collection` value here and not a new table), it must have its own sequence and cursor and must not reuse this one.
- `kv_store` is untouched by the v2 schema.

## 5. Decision: tombstone GC rule

- A delete is never a physical DELETE from a client. The client upserts a row with `deleted_at` set, `body` null and a newer HLC.
- Retention is 90 days. `forge_gc_tombstones(retain interval default '90 days')` deletes rows where `deleted_at < now() - retain`. It is `security definer`, with execute revoked from `public`, `anon` and `authenticated`.
- Scheduling is optional and needs the user to enable `pg_cron` in the dashboard (the schedule line in the SQL is commented out). Without it, GC is run by hand.
- Re-adding an id (undo in src/undo.js) is an upsert with a newer HLC and resurrects the record.
- A device offline for more than 60 days must not push stale state: it does a full pull and drops local records that are absent from the cloud, older than the pull start and not in its outbox. Sixty days is chosen to sit well inside the 90-day retention so a tombstone is still present when such a device returns. A device offline for more than 90 days is covered by the same full-resync rule.

## 6. Decision: treatment of all 17 keys in `SYNCED_KEYS`

`SYNCED_KEYS` in src/store.js (17 keys): settings, notes, progress, expenses, budgets, goals, examProgress, examNotes, investProgress, watchlist, tasks, reminders, habits, moodLog, loans, puzzleProgress, checklists. All 17 are covered below. R6-04 builds one adapter per key; the adapters turn the v1 value into records and back, so `getX/saveX/mutateX` keep their signatures.

Families (matches errata E-12): id-list 10 keys, flat map 4 keys, by-date 1 key, leaf map 1 key, document 1 key.

| Key | Family | `collection` | Record `id` | `body` | `pos` |
|---|---|---|---|---|---|
| settings | document | `settings` | `_` (single record) | the whole object `{cfHandle, theme, ...}`; the cream theme lives here (D15) | none |
| notes | id-list | `notes` | `String(item.id)` | the note, including `parentId` (tree) | yes, order is saved data |
| progress | flat map | `progress` | problem id (map key) | `{status, tags, updatedAt}` | none |
| expenses | id-list | `expenses` | `String(item.id)` | the expense | yes |
| budgets | flat map | `budgets` | category id (map key) | the number | none |
| goals | id-list | `goals` | `String(item.id)` | the goal | yes |
| examProgress | flat map | `examProgress` | `exam::section::topic` (map key) | the boolean | none |
| examNotes | id-list | `examNotes` | `String(item.id)` | the note | yes |
| investProgress | leaf map | `investProgress` | `<group>:<key>` for `done`, `quiz`, `tasks`; plus `current` | the leaf value (`current` is stored as its own record, skipped when null) | none |
| watchlist | id-list | `watchlist` | `String(item.id)` | the entry | yes |
| tasks | id-list | `tasks` | `String(item.id)` | the task, with `subtasks[]` still nested in the body | yes |
| reminders | id-list | `reminders` | `String(item.id)` | the reminder | yes |
| habits | id-list plus child | `habits` and `habitCheckins` | habit: `String(item.id)`; check-in: `<habitId>:<YYYY-MM-DD>` | habit without `checkins`; check-in `{habitId, date}` | habit: yes; check-in: none |
| moodLog | by date | `moodLog` | `YYYY-MM-DD` (the entry's `date`) | the entry | none |
| loans | id-list | `loans` | `String(item.id)` | the loan | yes |
| puzzleProgress | flat map | `puzzleProgress` | puzzle id (map key) | the boolean | none |
| checklists | id-list (legacy) | `checklists` | `String(item.id)` | the checklist; the key is drained to `[]` in the current code, so it is expected to hold few or no records | yes |

Rules that apply to every row of the table:

- A map entry is a record, and a bare `false` or `0` is a value, never a delete. Only `deleted_at` deletes.
- `settings` is one record, so concurrent edits to two different settings fields on two devices still resolve to one winner. That is accepted for a two-field document and revisited only if settings grows.
- `habits.checkins` becomes its own collection so two devices that check in on different days both survive. `tasks.subtasks[]` stays nested for now (a known remaining collision, deferred).
- Legacy ids can be numeric or duplicated (ids were `Date.now()` before commit deb249f). Ids are stringified, and the backfill keeps one row per id (`DISTINCT ON`).
- `pos` is the midpoint between neighbours, renumbered when exhausted. A reorder changes one record's `pos`, not every record.
- `saveX(wholeArray)` call sites are kept safe by the client "bridge" (R6-03): emit an op only for records changed against the version they were read at, tombstone only ids previously served to the UI, and treat a reorder as one `pos` change. A stale component snapshot therefore cannot delete or revert a record that arrived by sync.
- Level and XP stay derived and add no synced key (errata E-15, D2 default).

## 7. Decision: per-key flagged migration and rollback

Flag: `VITE_SYNC_V2_KEYS` (a comma-separated key list in the Vercel environment) with a per-device localStorage override. A key not in the list keeps using v1 exactly as today.

Steps, in order:

1. Backup. `create table kv_store_backup_20261112 as table kv_store` with RLS on and no policy (unreadable by the app, readable in the dashboard), plus the JSON export (X1-07), plus the untouched local `__pre_sync_backup` entries.
2. Backfill. `forge_backfill()` explodes each blob into records. `hlc` is derived from `kv_store.updated_at` with node `backfill`, so a re-run produces identical values (idempotent) and any real client edit has a newer HLC and wins.
3. Seed from local. v1's `cloud.write` ignores the `{error}` that supabase-js returns instead of throwing (R6 finding, fixed first by R6-01), so a past "synced" write may not be in `kv_store`. On first v2 launch each device pushes local records that are missing or newer in the cloud, so the cloud blob is not the only source.
4. Dual-write for 14 days. A v2 client also writes the v1 local shape and the `kv_store` blob (debounced at 5 s). Blob writes from a v1 device are imported additively, without tombstones, so a delete made on a stale v1 device in that window is lost. That loss is accepted and flagged to the user.
5. Verify before each cutover. The view `v2_verify` compares count and md5 of ids per key, blob against live, and every row must show `ok = true` before the key is flipped. Run it before flipping, because it will legitimately differ after v2 clients add or delete records. `habitCheckins`, `investProgress` and `settings` are verified by a client-side deep-equal of the materialized records against the blob.
6. Cutover order, lowest risk first. Stage 1: puzzleProgress, examProgress, examNotes, watchlist, progress, checklists. Stage 2: loans, goals, budgets, expenses, reminders, notes, tasks, investProgress. Stage 3: habits (with habitCheckins), moodLog, settings. R6's order did not list `checklists`; it is placed in stage 1 here because it is a drained legacy key with the least data.
7. Rollback per key: remove the key from `VITE_SYNC_V2_KEYS` (and clear the device override). Because `kv_store` is still dual-written during the window, v1 resumes with current data. Records stay in `records` and are ignored.
8. Full rollback: `drop table public.records cascade`, then drop `forge_push(jsonb)`, `forge_backfill(uuid)`, `forge_gc_tombstones(interval)` and `records_stamp()`. `kv_store` and `kv_store_backup_20261112` are untouched.
9. Retire v1 only after the 14-day window, once a per-device check (`count(distinct device_id)`) shows no v1 device is still writing (R6-18, P4). `kv_store` is kept even then.

`claimOwner` still wipes the single localforage instance on a user change. That instance now also holds the records, outbox, cursor and device id, so they stay consistent, and `r2:meta.userId` is checked before any push.

## Consequences

Good:
- Edits to different records on different devices both survive. Concurrent habit check-ins on different days both survive.
- Deletes are explicit and can be undone, and a stale device cannot resurrect them inside the retention window.
- A wrong device clock is bounded by the HLC receive rule and the 24-hour guard.
- Pulls are small deltas, and a failed or replayed push is harmless.
- Each key can be flipped back independently.

Costs and risks:
- A new table, trigger, RPC and a one-time migration, with a 14-day dual-write period that doubles local and cloud writes for one user.
- Whole-array `saveX` call sites need the bridge until they move to `useSynced(key).update(fn)`. Two live components holding stale copies of one key remain a residual risk.
- `tasks.subtasks[]` and the `settings` document still resolve per record, not per field.
- Deletes made on a stale v1 device during dual-write are lost (accepted).
- Two browser tabs doing read-modify-write on the same IndexedDB item can lose a write. R6 proposes Web Locks plus BroadcastChannel and calls it the least proven part, to be spiked first (R6-07).
- Free-tier Supabase projects can pause, which stops sync. Mitigation is outside this ADR (X1-08 keep-alive, X1-07 export, errata E-14).
- A device offline longer than the retention window depends on the 60-day full-resync rule being implemented correctly.
